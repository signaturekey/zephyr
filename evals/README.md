# Последующая оценка Zephyr

В этом каталоге хранится формат последующей оценки, описанный в разделе 18
`AGENTS.md`. Здесь намеренно нет выдуманных результатов эксплуатации. Добавляйте
записи по реальным уже завершённым PR в `cases/` только после того, как MVP
сформировал артефакт review для исходного проверяемого SHA.

Каждый сценарий должен:

1. однозначно указывать неизменяемый проверенный commit и базовый завершённый PR;
2. сохранять harness, run ID Zephyr, артефакт review и ограничения покрытия;
3. нормализовать релевантные комментарии людей в `human_findings`;
4. явно сопоставлять совпадения и классифицировать каждую находку только Zephyr
   как подтверждённую, ложноположительную или требующую решения человека;
5. сохранять идентификаторы пропущенных человеческих замечаний, а не скрывать
   слепые зоны;
6. не содержать исходный код, credentials, приватные обсуждения или цепочки
   рассуждений модели.

В `testdata/` лежат синтетические сценарии, которые проверяют формат и
классификацию: полное совпадение, пропуск из-за coverage limit, alignment,
несколько ролей на одну проблему и чистое изменение. Это тестовые данные, а не
метрики качества Zephyr. Для нового реального сценария скопируйте подходящий
файл, поместите его в `cases/`, установите `synthetic` в `false` и замените
значения реальными read-only доказательствами.

В `routing-cases/` лежат отдельные inputs для hybrid routing: контекстный шум,
явные frontend и SQL scopes и защищённые changed paths. Обычный `go test`
проверяет deterministic merge, provenance, полный учёт ролей и повторяемость
`routing.json`; он не подменяет собой проверку LLM-классификации.

Live semantic eval действительно передаёт dispatcher точные packet, request и
schema blocks и сравнивает выбранные роли. Для Codex сначала создайте свежий
compatibility descriptor, затем запустите:

```bash
ZEPHYR_ROUTING_EVAL_HARNESS=codex \
ZEPHYR_ROUTING_EVAL_COMPAT=/absolute/private/codex-compatibility.txt \
go test ./evals/... -run TestLiveSemanticRoutingClassification -count=1
```

Проверить схему, целостность ссылок и все сохранённые сценарии можно командой:

```bash
go test ./evals/...
```

В схеме намеренно нет числового порога «прошло/не прошло». План MVP использует
последующую оценку, чтобы показывать слепые зоны и ложноположительные результаты,
а не превращает фиксированный KPI в условие выпуска.
